## What this is

Marketing + booking site for Dogma Wine Bar (Porto). Astro static site deployed to Netlify, with Netlify
Functions handling payments (Stripe) and table/tasting bookings (resOS). Owner/subject of the site is
Vasilii Grebencea, Portugal's first Master of Port — the credential is the spine of the brand (see
`PRODUCT.md`).

## Commands

```bash
npm run dev       # astro dev — starts local dev server
npm run build     # astro build → dist/
npm run preview   # serve the built dist/ locally
```

No test suite and no linter configured. There is no separate typecheck script; TypeScript strict mode
(`astro/tsconfigs/strict`) is enforced by the Astro build itself — `npm run build` is the closest thing to
a check.

Netlify Functions live under `netlify/functions/` and run locally only via `netlify dev` (Netlify CLI is
installed; not part of `npm run dev`). Pretty paths (`/api/*`) are mapped to the underlying functions in
`netlify.toml`.

## Architecture

### Two-catalogue pattern (client display vs. server authority)

Prices, tasting/case details, and shipping rates each exist in **two places** that must stay in sync:

| Client display (`src/data/*.ts`) | Server authority (`netlify/lib/*.mjs`) |
|---|---|
| `tastings.ts` | `tastings.mjs` |
| `cases.ts` | `cases.mjs` |
| `shipping.ts` | `shipping.mjs` |

The client files are for rendering copy/images only. **The browser never sends a price** — every Netlify
Function recomputes the charge from its own `netlify/lib/*.mjs` catalogue. When changing a price or adding
a tasting/case category, both files need the matching update, keyed by the same `slug`.

### Booking flow (tastings)

Stripe Checkout (full payment upfront) + resOS (table reservation), wired so the guest never sees a
booking failure after paying:

1. `/bookatasting` (deep-linkable via `?tasting=<slug>`) → `POST /api/check-availability` →
   `netlify/functions/check-availability.mjs` → `netlify/lib/resos.mjs` asks resOS if the slot is free.
2. Guest submits details → `POST /api/create-checkout-session` →
   `netlify/functions/create-checkout-session.mjs` re-checks availability, computes the price server-side,
   creates a Stripe Checkout session with all booking data stuffed into `session.metadata` (the resOS
   booking is **not** created yet), redirects to Stripe.
3. Stripe fires `checkout.session.completed` → `netlify/functions/stripe-webhook.mjs`:
   - re-checks resOS availability one more time (the slot could have been lost during checkout) — if lost,
     auto-refunds via Stripe and notifies Telegram instead of creating a booking;
   - otherwise creates the resOS booking with `status: "approved"` (resOS booking API only accepts
     `"request"` or `"approved"`, not `"confirmed"`);
   - idempotent via `paymentIntent.metadata.resosBookingId` so Stripe retries don't double-book;
   - sends a Telegram notification either way (see `netlify/lib/notify.mjs`).

Signature Cases (wine case orders) follow the same Stripe-first pattern but ship physically instead of
booking a table — `create-case-checkout.mjs` computes wine + shipping price from `cases.mjs` +
`shipping.mjs`, and the webhook's `kind === "case"` branch just notifies Telegram (no resOS involved).

resOS auth is HTTP Basic with the API key as username, empty password (`netlify/lib/resos.mjs`). Required
env vars: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `RESOS_API_KEY`, plus Telegram bot vars consumed by
`notify.mjs`. These live only in Netlify env vars, never in client code.

### Shared request handling

`netlify/lib/http.mjs` centralizes what every function needs: CORS/origin checks (`pickOrigin`,
`isDisallowedOrigin`), per-IP rate limiting (`rateLimit`), and input validators (email/phone/date/time
guards). All four functions follow the same shape: OPTIONS preflight → method check → origin check → rate
limit → honeypot (`botField`) → field validation → business logic.

### Content/data layer

Pages under `src/pages/*.astro` pull copy and structured data from `src/data/*.ts` rather than hardcoding
it inline — `site.ts` (contact info, nav, hours), `home.ts`, `tastings.ts`, `services.ts`, `cases.ts`,
`shipping.ts`, `menu.ts`. `menu.ts` is regenerated by a scheduled weekly sync from source PDFs (Mondays) —
don't hand-edit menu content expecting it to persist without checking that automation.

`services.ts` and `home.ts` both enforce (by convention, not code) that only *live, bookable*
categories are listed — don't add a service/nav entry without a real destination page.

### Design system

Locked design tokens (colors, type scale, spacing, components) are documented in `DESIGN-HANDOFF.md` and
implemented as CSS custom properties in `src/styles/global.css`. Key facts: deep burgundy (`--wine-900`) +
cream (`--cream`) + restrained gold (`--gold`) palette; gold passes AA contrast **only on burgundy**, never
on cream (use `.eyebrow--ink` there); Playfair Display for headings, Inter for body, JetBrains Mono for
prices/numerals; all spacing/type is fluid via `clamp()`, no fixed-px layouts. New pages/components should
reuse existing tokens and components (buttons, eyebrow, medallions, footer) rather than inventing new
styles — see `DESIGN-HANDOFF.md` §1–3 before designing anything new.

`src/layouts/Base.astro` is the single page shell: fonts, global CSS, SEO meta + JSON-LD (`LocalBusiness`
schema), Header/Footer/CookieConsent. Props (`headerSolid`, `bareFooter`, `noindex`) control per-page
header/footer variants — inner pages pass `headerSolid` for a readable nav over non-hero content; Home
merges its Visit section with the footer via `bareFooter`.

## Project-specific constraints

- Never invent placeholder logos, photos, or text stand-ins for missing assets — ask for the real file.
  The photo library lives at `/Users/mrsmoke/Desktop/DOGMA MATERIAL/` outside this repo.
- The 6 tastings' names, slugs, and prices are fixed (owned by Vasilii) — see the table in
  `DESIGN-HANDOFF.md` §5. Durations are the only still-open field.
- Git commit/push/merge for site changes is pre-authorized — no need to ask before each one.
- **Internal links must end in a trailing slash** (`/menu/`, not `/menu`). Netlify 301s the
  non-slashed form, and `Header.astro` compares `Astro.url.pathname` (always slashed) against
  `nav[].href` — a missing slash silently kills `aria-current`/`.nav__link--active` sitewide.
  This applies to `src/data/*.ts` hrefs too, anchors included (`/bookatasting/#port-intro`).
